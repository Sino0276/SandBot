# 거리·컬러 센서와 AprilTag 비전(4c·4d) 기준 문서

이 문서는 SandBot 시뮬레이터의 4c 단계(REV 2m 거리 센서·REV Color Sensor V3)와 4d 단계(웹캠 AprilTag 비전)가 쓰는 모든 치수·상수·표·수식·결정사항을 한곳에 적는다. 원본 조사·명세 문서(`p13field/spec-4c.md`, `p13field/spec-4d.md`, `p13field/research/synthesis.md`, 비평 문서와 부록 A·B의 Python 스크립트)는 저장소 밖 작업 폴더에 있다가 사라졌으므로, 코드(`src/shared/sim/fieldRaycast.ts`·`rangeSensor.ts`·`colorSensor.ts`·`sensorNoise.ts`·`fieldSensors.ts`·`sensorFrame.ts`·`cameraData.ts`·`vision.ts`·`fieldCameras.ts`, 사이드카 `VL53L0XChip`·`ColorSensorV3Chip`·`SandbotCameraModels`·`SandbotCameraCalibrations`·`SimCamera`·`VisionPortalImpl`·`AprilTagProcessorImpl`·`org.sandbot.sdk.vision.*`, 렌더러 `hardware/mounting.ts`·`hardware/catalog.ts`·편집기 표시 모듈)와 CLAUDE.md의 서술이 곧 원본이다. 값마다 값 · 단위 · 위치(파일·상수·함수 이름, 줄 번호 없음) · 상태(코드 주석의 `[확인: …]`·`[가정: …]`·`[결정: …]`, 표시 없는 코드 값)와 근거를 적었고, 코드에 출처가 없으면 "출처 기록 없음"이라고 썼다. 수식은 코드의 변수 이름을 그대로 써서 다시 구현할 수 있게 했다. 이 문서가 식을 다시 계산해 얻은 수치는 "계산값"이라고 표시했다(코드에 그 글자가 없다). 필드 데이터(벽·테이프·구조물·태그의 치수)는 `field-biobuzz.md`(4ab)가 주인이고 여기서는 센서·카메라가 읽는 부분만 되풀이한다.

## 0. 읽는 법

### 0.1 상태 표기

코드 주석의 표기를 그대로 쓴다.

| 표기      | 뜻                                                                               |
| --------- | -------------------------------------------------------------------------------- |
| [확인: …] | 데이터시트·SDK 소스·OpenCV 소스·공식 CAD에서 확인한 값. 주석이 출처를 적는다     |
| [가정: …] | 출처 없이 정한 값. 실측으로 바꿀 대상(`docs/assumptions.md`에도 한 줄이 있다)    |
| [결정: …] | 설계로 정한 값(재는 값이 아님). 사용자가 정한 것은 "사용자 결정"으로 따로 적는다 |
| 코드 값   | 주석에 태그가 없는 값. 주석의 설명만 옮겼다                                      |
| 계산값    | 코드에 그 글자가 없고 이 문서를 쓸 때 코드의 식으로 다시 계산한 값               |
| 환산      | 이 문서가 단위만 바꾼 값. 1 in = 0.0254 m                                        |

주석이 가리키는 `spec-4c §…`, `spec-4d §…`, `synthesis §…`, `critique X2`, `부록 A`·`부록 B` 같은 번호는 원본이 사라져(§24) 이 저장소에서 따라갈 수 없다. 그 번호는 "주석 인용"으로만 적었다.

### 0.2 단위·표기 규약

- 코드의 길이는 미터, 각은 라디안, 시간은 정수 나노초(`tNanos`)다. 표의 `in`·`°`·`ms`는 환산이다.
- 필드 좌표는 FTC 필드 좌표(원점 중앙 타일 윗면, Z 위)다. 회전은 X(롤)·Y(피치)·Z(요) 라디안이고 적용 순서는 `'ZYX'`, 곧 R = Rz·Ry·Rx다. 3×3 행렬은 모두 행 우선 9원소 배열이다.
- 센서 틀: 원점은 하우징 앞면, +X가 보는 방향, +Z가 광선 방위각의 기준이다(§2).
- 위치 열은 파일 경로와 상수·함수 이름이다. `rangeSensor.ts` 등 `src/shared/sim/` 아래 파일은 폴더를 생략했다. 렌더러·사이드카 파일은 `src/renderer/src/…`·`sidecar/sdk/…`부터 적었다.
- `abs(x)`는 절댓값이다(표 안에서 세로 막대 기호를 피하려고 이렇게 썼다).

### 1.2 데이터 흐름

시뮬레이터 세계(`world.ts`, `PhysicsWorld`)는 틱 경계마다 한 번 입력을 만든다. 센서·카메라는 하위 단계(1 ms 이하)에서는 계산하지 않고 틱 경계에서만 계산한다. 한 경계의 입력 순서는 다음이다(입력 키 순서가 프로토콜 바이트에 들어가므로 순서를 바꾸지 않는다).

1. 기존 입력(모터 position·velocity, 허브 voltage, 데드휠, IMU, Pinpoint, OTOS 등)
2. 거리 센서 목록(세계 설명 순서): `distance`
3. 컬러 센서 목록(세계 설명 순서): `red`·`green`·`blue`·`proximity`
4. 웹캠 목록(세계 설명 순서): `model` → (프레임 틱이면) `frameNanos`·`frameWidth`·`frameHeight`·`tags`

센서가 없는 세계는 입력열이 4c 전과 바이트 그대로이고, 웹캠이 없는 세계는 4d 전과 바이트 그대로다(CLAUDE.md의 기준 해시 여섯째가 4c 센서, 일곱째가 4d 웹캠 기준이다).

### 1.3 입력 키

| --------- | -------------------------- | ------------------------ | ----------------- | --------------------------------------------------------------------------------------------------------------- |
| 거리 센서 | `distance`                 | m(1 mm 반올림) 또는 null | `fieldSensors.ts` | 범위 밖이면 null을 명시해 보낸다(입력은 합쳐지므로 키를 빼면 이전 값이 남는다). 칩은 null·없음을 8190 mm로 본다 |

### 2.2 조준(시뮬레이터 전용 속성)

거리·컬러 센서와 웹캠의 조준은 SDK 값이 아니라 팀이 넣는 시뮬레이터 전용 값이다. 생성 Java·구성 XML은 바이트 그대로다(CLAUDE.md). 속성을 더하거나 기본값을 바꿔도 `PROJECT_VERSION`을 올리지 않는다(`parseProps`가 기본값을 채운다).

### 3.2 교차 순서와 규칙

`cast(origin, dir, maxT)`는 바닥 → 벽 → 구조물(배열 순서) 순으로 보고 더 작은 t만 바꾼다(같은 t면 앞의 것). 모든 후보는 t ≥ `MIN_RAY_T`다.

| 대상                   | 조건·식                                                                                                                                                                                                                                                                                   |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 바닥(z = 0)            | d.z < 0이고 o.z > −`SURFACE_TOLERANCE`일 때만. t = max(`MIN_RAY_T`, max(o.z, 0)/(−d.z)). 맞은 점이 필드 안(abs(x), abs(y) ≤ innerHalf)일 때만. cosIncidence = −d.z. 재질은 점을 닫힌 사각형으로 처음 덮는 테이프(`FieldSpec.tape` 배열 순서, `offField` 테이프는 뺌), 없으면 바닥 재질    |
| 벽                     | 후보 순서 +x, −x, +y, −y(바깥 법선 n). 조건 d·n > `PARALLEL`이고 o·n < innerHalf + `SURFACE_TOLERANCE`. ct = max(`MIN_RAY_T`, (innerHalf − o·n)/(d·n)), 가장 작은 ct(같으면 앞 벽). 그 평면의 점으로 분류: reach = max(0, (innerHalf − o·n)/(d·n)), z = o.z + reach·d.z, s = 벽 방향 좌표 |
| 벽 분류 1: 레일        | z가 레일 띠(`railBands`) 어느 하나에 닫힌 구간으로 들면 레일 면(t = ct, 레일 재질, cosIncidence = d·n)                                                                                                                                                                                    |
| 벽 분류 2: 투명판      | z가 판 구간 (railBands[0][1], railBands[1][0])(열린 구간)에 들고 s가 판 이음(`panelSeams`, 닫힌 구간) 밖이면 판 안쪽 면 tp = max(`MIN_RAY_T`, (innerHalf + panelInset − o·n)/(d·n))에서 헤이즈(rgb·nir 0.01)로 맞는다. 분류는 레일 면의 z로 한다(판까지 2.3 mm 차이는 무시)               |
| 벽 분류 3: 지나감      | 위 레일 위(z가 두 띠 밖)와 판 이음 높이 광선은 지나간다(필드 밖 형상 없음). 판 이음에서 레일은 이어진다                                                                                                                                                                                   |
| 구조물                 | `sensed`이고 `carrier === 'field'`인 것만, 배열 순서. 넓은 단계: 경계 구(반지름 = 반 대각선 + 1e-9, 원기둥은 hypot(r, 반 높이) + 1e-9)로 거른다. 좁은 단계: 상자 slab 교차(축 순서 x, y, z, 같은 t면 앞 축)·세운 원기둥 교차(옆면·뚜껑). 자기 틀 변환은 Rᵀ·(p − 중심)                     |
| 구조물: 나란함         | 상자 slab은 축마다 abs(d) < `PARALLEL`이면 그 축을 나란하다고 보고(원점이 그 축 반 길이 밖이면 빗나감), 세운 원기둥 옆면은 d.x² + d.y² > `PARALLEL`²(1e-24)일 때만, 뚜껑은 abs(d.z) ≥ `PARALLEL`일 때만 본다. 모두 t > 0인 들어가는 면만 후보다                                           |
| 구조물: 원점이 안일 때 | 가장 가까운 면까지 깊이(같은 깊이면 상자는 +x, −x, +y, −y, +z, −z 순서, 원기둥은 옆면·위·아래 순서)가 `SURFACE_TOLERANCE` 이하이고 광선이 그 면에서 안쪽으로 갈 때만 그 면에 `MIN_RAY_T`로 맞는다. 더 깊으면 그 구조물을 무시한다(걸친 시작을 밀어내지 않는 4ab 규칙과 같은 쪽)           |
| 구조물: cosIncidence   | abs(d·n_field), n_field = 자기 틀 법선을 필드로 옮긴 것                                                                                                                                                                                                                                   |

`blocked(origin, dir, maxT, flag)`는 (0, maxT) 안에 `flag`('sensed': 4c 거울 가림, 'occludes': 4d 카메라 가림)가 참인 field carrier 구조물이 있는지 본다. 원점이 구조물 안(닫힌)이면 그 구조물은 가리지 않는다. 조건은 entry.t < maxT다.

`panelMirrors(origin, axis)`는 벽 순서 +x, −x, +y, −y로 거울 후보를 낸다. 후보 조건은 모두 참이어야 한다.

1. 조준 축과 벽 바깥 법선의 각 angle = acos(clamp(axis·n)) ≤ 12.5°(`MIRROR_HALF_ANGLE`)
2. 판 안쪽 면까지 수직 거리 D = (innerHalf + panelInset) − origin·n이 0 < D ≤ `MAX_RAY_RANGE`
3. 수선의 발 foot = origin + D·n의 z가 판 구간 (railBands[0][1], railBands[1][0]) 안
4. 발의 벽 방향 좌표 s가 abs(s) ≤ innerHalf이고 판 이음 밖
5. 수선(origin → foot, 길이 D)을 `sensed` 구조물이 가리지 않음

### 3.3 'none' 시즌

'none' 시즌도 같은 외곽 모델이다(레일 띠·판 재질·이음은 BIOBUZZ 값, 반폭·높이만 `field.ts` 값). 구조물이 없고 테이프가 없다.

### 5.2 광선 배치(센서 틀)

고리 0은 축 광선 하나다. 고리 k ≥ 1의 중심각은 θ_k = acos(1 − (1 − cos α)·m_k/61)이고 m_k = (앞 고리 광선 수의 합) + n_k/2다. 방위각은 ψ_j = 2π·(j + o_k)/n_k(j = 0…n_k−1), 고리 k가 홀수(1·3)이면 반 칸 엇갈림 o_k = 0.5, 짝수는 0이다. 방향은 (cos θ, sin θ·sin ψ, sin θ·cos ψ)(ψ = 0이 센서 +Z, +Y 쪽으로 감). 무게는 w = P(θ)/ΣP(광선 순서로 합)다. 광선 순서는 고리 0 → 1 → 2 → 3 → 4, 각 고리 안에서 j 순서다(결과 배열 `TOF_RAYS`, 얼린 객체이고 `RangeReading.rays`·기즈모 모선이 같은 순서를 쓴다). 모듈이 읽힐 때 계산한다(리터럴로 두면 Python 값과 V8 값이 ulp 단위로 다르다).

### 5.3 신호와 보고 거리

광선 k가 맞은 t, 입사각 τ(cosIncidence = cos τ), 재질 ρ_nir에 대해 (t는 max(t, `MIN_RAY_T`)):

- 확산 신호 s_k = w_k·ρ_nir·cos τ / t²
- 확산 합 S_d = Σ s_k, 확산 가중 합 T_d = Σ s_k·t_k
- 투명판 거울 후보(§3.2 `panelMirrors`) j마다: D_j = 판 안쪽 면까지 수직 거리, φ_j = 축과 벽 법선의 각, g_j = P(φ_j)/P̄, 신호 s_j = C·0.514·g_j / D_j². S_m = Σ s_j, T_m = Σ s_j·D_j
- 전체 신호 S = S_d + S_m. S ≤ 0이면 신호 없음(distance null)
- 보고 거리(raw) d = (T_d/B + T_m)/S (B는 확산 광선에만 나눈다)
- 유효 반사율 ρ_eff = S·d²/C
- 문턱 d_max(ρ_eff)(§5.4)를 구해 raw ≤ d_max이면 보내고, raw > d_max이면 범위 밖 null(칩 8190 mm)
- `surface`는 면별 신호 합(같은 면끼리 합침, 처음 나온 순서: 축 광선부터 광선 순서, 거울은 마지막)이 가장 큰 면. `rays`는 광선마다 맞은 t(빗나가면 null, 기즈모 모선용)

정면 램버트 평면(거리 D, 반사율 ρ)에서는 t_k = D/cos θ_k, cos τ = cos θ_k이므로 s_k = w_k·ρ·cos³θ_k/D², S = ρ·C/D², T_d/S = D·B이고 raw = D, ρ_eff = ρ다. 정면 판(φ = 0)은 거울 항만 보면 S = C·0.514·g(0)/D², raw = D, ρ_eff = 0.514·2/P̄ = 1.0263(계산값)이라 d_max = 1.2 m(흰색 상한)다. 같은 판은 61광선에 헤이즈(nir 0.01)로도 확산 신호를 내므로 실제 ρ_eff는 거기에 약 0.01이 더해진 약 1.036이다(시험이 1.036 ± 2e-3으로 고정, §22.1 A9). 정면 평면·정면 판·둘이 섞인 것 모두 정확히 D다(주석).

### 6.2 식

축 광선(센서 +X)의 맞은 면까지 거리 t_axis, 입사각 cos τ = cosIncidence. 발자국 7광선은 축 + 바깥 6광선(센서 틀에서 축에서 β = atan(0.6) 기울고 방위각 0°, 60°, …, 300°, 센서 +Z부터 +Y 쪽)이며 정면 평면에서 반경 0.6·d의 점이다. 각 광선이 맞은 재질에서 평균을 낸다(n = 7).

- d = max(t_axis, 0.25 in) (m), d_in = d / 0.0254
- 낙하 falloff = d_in^(−1.3169), 그늘 shade = d/(d + 0.01)
- ρ̄^L_c = (1/7)·Σ(광선이 맞은 면의 rgb_c, 빗나가면 0, 판에 맞으면 헤이즈 0.01) — LED 반사
- ρ̄^A_c = (1/7)·Σ(맞은 면의 rgb_c, 빗나가거나 판에 맞으면 ρ_bg = 0.2) — 주변광
- ρ̄^N = (1/7)·Σ(맞은 면의 nir, 빗나가면 0, 판이면 헤이즈 0.01) — 근적외
- raw_c = clamp(round(wb_c·[ρ̄^L_c·K·cos τ·falloff + ρ̄^A_c·E_a·shade/1.1834]), 0, 65535), c = red·green·blue. 곱 순서는 부록 A 기준 스크립트(`s4c2/sim2.py`)와 같게 둔다(정수 반올림 경계에서 같게)
- PS = clamp(round(26.98 + 325.961·(ρ̄^N/0.5)·cos τ·falloff), 0, 2047)
- 축 광선이 빗나가면(맞은 것이 없음) 배경만: raw_c = round(wb_c·0.2·500/1.1834) = (79, 85, 55), PS = 27, distance null(모듈 상수 `COLOR_BACKGROUND_READING`, 인스펙터·비유한 방어가 같은 값을 쓴다). 판 정면(축이 판에 맞음)은 판에 헤이즈 + 판 너머 배경으로 계산한다(예: 'none' 벽 판 정면 0.05 m, 높이 0.14 m → (68, 73, 47), PS 30, 시험 기준)
- 컬러에는 거울 반환과 잡음이 없다(근거가 없다)

타일(nir 0.2) 위 `getDistance`는 실제 거리의 약 2배다(가정들의 결과: REV의 역공식이 card stock(nir 0.5) 기준이라 d_rep = d·(0.2/0.5)^(−1/1.3169) = 2.005·d, 계산값). 인스펙터가 실제 거리를 함께 보인다.

LS_MEAS_RATE[2:0] 주기(DS p.20): 0 → 25 ms, 1 → 50, 2 → 100, 3 → 200, 4 → 500, 5 → 1000, 6 → 2000, 7 → 2000 ms. 실제 주기 P = max(그 주기, 적분 시간 t_int)("repeat rate will be lower than programmed").

| 0: 1×              | 28.8288  | 3.6036 | 1.8018 | 0.9009 | 0.4505 | 0.2252 |
| 1: 3×              | 9.4675   | 1.1834 | 0.5917 | 0.2959 | 0.1479 | 0.0740 |
| 2: 6×              | 4.7267   | 0.5908 | 0.2954 | 0.1477 | 0.0739 | 0.0369 |
| 3: 9×              | 3.1189   | 0.3899 | 0.1949 | 0.0975 | 0.0487 | 0.0244 |
| 4: 18×             | 1.5459   | 0.1932 | 0.0966 | 0.0483 | 0.0242 | 0.0121 |

이득 코드가 4보다 크면 3×(DS 기본, 행 1)로 본다. 입력은 3×·25 ms 기준이므로 척도 r = 1.1834 / res(이득, 적분 열)이고, SDK 기본 설정이면 r = 1이다.

PS_MEAS_RATE[2:0] 주기(DS p.19): 0(예약) → 6.25 ms, 1 → 6.25, 2 → 12.5, 3 → 25, 4 → 50, 5 → 100, 6 → 200, 7 → 400 ms.

측정 시각과 값(주석 인용 명세 4c §1.8, DS 상태도 해석 [가정: LS는 적분 창 평균] [가정: PS는 순간]):

- LS 위상 기준 t_ls = LS_EN 0 → 1 때, 그리고 LS_MEAS_RATE·LS_GAIN 쓰기 중 나중 것("Writing to this register resets LS state machine"). 변환이 먼저라 측정 k(≥ 0)는 t_ls + t_int + k·P에 끝난다. LS_DATA는 마지막으로 끝난 측정 값(첫 측정 전 0)이다.
- LS 값: 측정 k의 값은 [끝 − t_int, 끝] 안 입력의 시간 가중 평균 → 척도 r → 반올림 → 포화(2^비트 − 1, 0 이상) 순서다. 입력은 틱 경계에서만 바뀌므로 입력 훅이 쌓은 구간(닫힌 구간 목록, 가장 이른 구간은 앞으로 늘림)으로 정확히 더한다. 다음 측정 창보다 앞에서 끝난 구간은 버린다.
- PS 위상 기준 t_ps = PS_EN 0 → 1 때, 그리고 PS_LED·PS_PULSES·PS_MEAS_RATE 쓰기 중 나중 것. 32펄스 변환(약 0.5 ms)은 0으로 보아 측정 k(≥ 0)는 t_ps + k·P_ps에 끝나고 그 순간의 PS 입력을 잡는다. PS_DATA는 마지막 PS 측정 값(첫 측정 전 0). PS 넘침 비트는 세우지 않는다(드라이버가 0x7FF로 가린다). PS는 SDK 기본 설정 기준이다(펄스·전류·해상도를 바꿔도 같은 값, 한계).
- 입력 키: `red`·`green`·`blue`·`ir`(없으면 0), `proximity`(0..2047, 없으면 0), 시험용 `distance`(m): RevColorSensorV3의 거리 공식을 거꾸로 써서 PS = round(A·inches^(1/(−0.75934)) + C), A = 325.961, C = 26.980, inches ≤ 0이면 2047, 0..2047로 자름. 시뮬레이터는 red·green·blue·proximity만 보낸다.

### 10.5 Field 인스펙터의 AprilTag 묶음 줄(`clusterLines.ts`)

지금 HIVE 상태(실행이 잠그면 실행의 상태)의 `clusterFieldPoses`를 묶음마다 "VectorF(…f) in · Quaternion(w, x, y, z, 0)" 한 줄로 보이고 [복사]는 `AprilTagClusterMetadata` 생성자의 뒤 세 인수(`new VectorF(…), DistanceUnit.INCH, new Quaternion(…)`, 같은 숫자 글자)를 복사한다. 위치는 in 소수 4자리(`INCH_DIGITS`, 0.1 mm 아래), 사원수는 소수 7자리(`QUATERNION_DIGITS`, Java float 유효 자릿수 7자리와 같은 정밀도)다. "-0.0000"은 "0.0000"으로 바꾼다. SDK `computeRobotPose`는 묶음 `fieldPosition`을 늘 인치로 쓰고(AprilTagProcessorImpl.java:498–500 인용), 현재 게임 라이브러리에는 묶음 멤버 id가 겹쳐 `setAllowOverwrite(true)`로도 더할 수 없으므로 BIOBUZZ가 없는 라이브러리에 넷을 더해야 한다(인스펙터 도움말).

묶음 원점(`tagPoses.ts`): SDK `getBioBuzzTagLibrary`(Vision 12.0 `AprilTagGameDatabase.java:198–216`)의 묶음 멤버 위치(묶음 틀, in)는 x가 첫 id부터 −6.50·−2.75·2.75·6.50(`SDK_BIOBUZZ_CLUSTER_MEMBER_X`), y 7.1874f(`SDK_BIOBUZZ_CLUSTER_OFFSET_Y`, Java float 리터럴이라 `Math.fround`), z −5.622f(`SDK_BIOBUZZ_CLUSTER_OFFSET_Z`)다. 묶음 틀 축은 멤버 태그 축과 같다. 묶음 원점 = 첫 멤버 태그 중심 − R_tag·(x_k, offY, offZ)·0.0254(k = 묶음 안 id 오름차순 순번, k = 0). 사원수는 [w, x, y, z](Hamilton, RobotCore `Quaternion.toMatrix`가 쓰는 능동 회전 묶음 틀 → 필드, w ≥ 0으로 정규화, Shepperd 방식으로 계산)이다. SDK 라이브러리 묶음 순서(`SDK_CLUSTER_ORDER`)는 RED SCORING(태그 30–33), RED AUDIENCE(34–37), BLUE AUDIENCE(38–41), BLUE SCORING(42–45)이다(파랑은 빨강 id + 8, 이름 짝은 RED SCORING ↔ BLUE AUDIENCE, RED AUDIENCE ↔ BLUE SCORING). SDK BIOBUZZ 라이브러리의 묶음 metadata는 필드 위치가 (0, 0, 0)이고 방향이 단위 사원수라 `robotPose`가 묶음 틀 기준이다(§16, notice `aprilTagNoFieldPose`).

### 11.3 SDK가 고르는 보정(`sdkCalibration`)

RobotCore 12.0 `CameraCalibrationManager.internalGetCalibration`을 옮긴 것이다(주석: spec-4d §1.13 인용).

3. 같은 종횡비가 없으면 placeholder(`PlaceholderCalibratedAspectRatioMismatch`).

## 13. 비전 투영·판정(`vision.ts`)

기하만 한다(처리 시간·프레임 버퍼·자세 풀이는 사이드카). 순수·결정적이다.

### 13.1 픽셀 좌표 둘

| 좌표            | 정의                                                                                     | 쓰이는 곳                 |
| --------------- | ---------------------------------------------------------------------------------------- | ------------------------- |
| OpenCV 좌표     | 첫 픽셀 중심이 (0, 0), x 오른쪽, y 아래. 보정 XML의 cx·cy가 이 좌표                      | 투영·판정·인스펙터·기즈모 |
| apriltag 3 좌표 | 왼쪽 위 픽셀의 왼쪽 위 모서리가 (0, 0) = OpenCV + `APRILTAG_PIXEL_ORIGIN`(0.5, x·y 모두) | 세계 입력 `tags`의 꼭짓점 |

`APRILTAG_PIXEL_ORIGIN` = 0.5: [확인: apriltag.c:538–552 `value_for_pixel`의 floor(px − 0.5), :818 `refine_edges`의 delta = 0.5, v3.4.2 `apriltag_quad_thresh.c:634` "adjust for pixel center bias"]. SDK가 이 꼭짓점을 OpenCV 보정과 함께 solvePnP에 넣으므로 실제 로봇처럼 자세에 (+0.5, +0.5) px 치우침이 있다(부록 B 장면에서 약 0.04 in·0.025°, CLAUDE.md).

### 13.2 투영

필드 점 P → 카메라 좌표: c = CV_FROM_SENSOR · Rᵀ · (P − O)(R, O = 센서 자세, Rᵀ·d의 성분은 센서 축(R의 열)과의 내적). 핀홀 투영: u = fx·c.x/c.z + cx, v = fy·c.y/c.z + cy(참 렌즈 값, 왜곡 없음). [결정: spec-4d §7, 참 렌즈 값으로 투영하고 왜곡은 넣지 않는다]. 렌즈 값은 (모델, w, h)마다 `trueIntrinsics`를 한 번 계산해 배열에 둔다(Map 순서에 기대지 않게).

태그 하나의 기하(`TagEntry`, 생성자에서 `hiveTipped`로 한 번 푼다): 태그 크기 s = 0.08255 m(검은 테두리 바깥 변, SDK 라이브러리 3.25 in, `TAG_SIZE`), half = s/2 = 0.041275. 태그 틀 점 (u, v, 0)·half의 필드 좌표 = 위치 + R_tag·(u·half, v·half, 0). 앞면 법선(필드) = −z_tag = (−r2, −r5, −r8). 태그 틀은 SDK 관례(x 오른쪽, y 그림 아래, 앞면 법선 −z)이고 꼭짓점은 apriltag 순서(영상 왼쪽 아래부터)다.

### 13.4 세계 입력 `tags`(`tagsInput`)

보이는 것만, id 오름차순, 최대 64개. 태그마다 `[id, x0, y0, …, x3, y3]`. 꼭짓점 = corners + 0.5(apriltag 3 좌표). 잡음을 켰으면 그 뒤 꼭짓점 좌표마다 `TAG_CORNER_NOISE_PX` = 0.3 px × `noiseGaussian(seed, device, id·8 + i, frameNanos)`를 더한다(i = 꼭짓점·2 + 축). 판정은 잡음 전이라 검출 여부가 바뀌지 않는다. 상태: [가정: 꼭짓점 잡음 σ 0.3 px, 기본 끔]. 측정: 고정한 카메라·태그로 100프레임의 꼭짓점 표준 편차.

### 13.5 사이드카 웹캠 출력 읽기(`readCameraOutputs`)

그 틱 출력에서 `streaming === true`, `width`·`height`가 1–4096 정수, `aprilTag` boolean, `family` 문자열 또는 null, `decimation` 유한 수(없으면 3, 1보다 작으면 1)일 때만 값이고, 아니면 null이라 그 틱에 프레임을 만들지 않는다. AprilTag 패밀리 중 시뮬레이터가 검출하는 것은 `TAG_36h11`뿐이다(`SIMULATED_TAG_FAMILY`).

## 15. 사이드카 VisionPortal 상태 기계와 처리 시간

`VisionPortalImpl`은 실제 12.0 소스에서 출발한 손 구현이다. 실제는 EOCV 카메라(`OpenCvWebcam`)와 카메라·상태 스레드로 돈다. SandBot에는 카메라 스레드가 없어 같은 상태 기계를 가상 시간으로 돌린다. 상태 전이와 프레임은 OpMode 스레드의 틱 경계 듣기(`Sim.BoundaryListener`)에서만 바뀐다. 바꾼 줄은 모두 `// SandBot:`이다.

### 15.1 전이 시간

| 전이                                                         | 시간 | 단위 | 위치                                 | 상태·근거                                                       |
| ------------------------------------------------------------ | ---- | ---- | ------------------------------------ | --------------------------------------------------------------- |
| 카메라 열기(`OPENING_CAMERA_DEVICE` → `CAMERA_DEVICE_READY`) | 1.0  | s    | `SANDBOT_OPEN_NANOS` = 1_000_000_000 | [가정: 포털 전이 시간]                                          |
| 스트림 시작(`STARTING_STREAM` → `STREAMING`)                 | 0.5  | s    | `SANDBOT_START_NANOS` = 500_000_000  | 같은 가정                                                       |
| 스트림 멈춤(`STOPPING_STREAM` → `CAMERA_DEVICE_READY`)       | 0.3  | s    | `SANDBOT_STOP_NANOS` = 300_000_000   | 같은 가정                                                       |
| 닫기(`CLOSING_CAMERA_DEVICE` → `CAMERA_DEVICE_CLOSED`)       | 0.3  | s    | `SANDBOT_CLOSE_NANOS` = 300_000_000  | 같은 가정. 처리 중이던 프레임의 결과 끝이 더 늦으면 그때 닫힌다 |

측정 방법(`docs/assumptions.md`): `getCameraState()`를 폴링하며 `ElapsedTime`으로 전이 시각을 기록한다. 상태: 실측 필요.

규칙:

- 전이 끝은 "시작 + 시간" 이후 첫 틱 경계에서 적용한다(끝 시각 ≤ b인 전이를 끝낸다).
- 열기 성공(`onOpened`): `CAMERA_DEVICE_READY` → 보정 조회(`SandbotCameraModels.identity(model)`, `SandbotCameraCalibrations.getCalibration(identity, w, h)` 한 번) → autoStart이면 같은 콜백에서 `STARTING_STREAM`(경계에서 READY는 보이지 않는다)으로 가고 시작 전이를 건다.
- 열기 실패: 같은 웹캠을 다른 포털이 잡고 있으면(`SimCamera.claim` 실패) 열기 시간 뒤 `ERROR`("Camera opening failed."). [가정: 같은 카메라 두 번 열기는 실패]. 실제 동작을 확인하지 못했다.
- stop·resume·close는 실제 `userStateSemaphore`처럼 진행 중 전이가 있으면 `awaitNextTick`으로 기다린다. 틱 경계 안(수명 리스너 등)이나 시간이 흐르지 않을 때는 다음 경계를 기다릴 수 없어 전이 끝까지 시간을 청구(charge)해 그 자리에서 적용한다.
- 스트림 형식 없이(`setStreamFormat` 없이, Builder 기본 null) `resumeStreaming`하면 실제 12.0의 카메라 스레드 NPE처럼 `STARTING_STREAM`에 머물고 notice `visionResumeNullFormat`이다(생성자 autoStart는 null을 견딘다). 실제 NPE가 앱을 멈추는지 확인하지 못했다.
- 뷰 컨테이너: `DEFAULT_VIEW_CONTAINER_ID` = 0x7F0A0000(`Integer.valueOf(0x7F0A0000).intValue()`, 상수식이 아니라 ConstantValue가 없다, 실제도 같다). [가정: RC 앱 R.id 꼴]. `makeMultiPortalView`의 뷰 id는 0x7F0A0001부터 올린다(`sandbotNextViewId`)이고 실제 `splitLayoutForMultipleViewports` 규칙(null layout은 실제처럼 NPE)을 옮겼다. LiveView는 아무것도 하지 않는다. `getFrameBitmap`은 아무것도 하지 않는다(`Continuation`이 stub이라 팀 코드가 만드는 데서 먼저 `SimUnsupportedException`으로 멈춘다). `saveNextFrameRaw`는 notice `visionFrameCapture`만 낸다(영상이 없다).
- 켜진 AprilTag 처리기가 둘 이상이면 첫 것을 쓰고 notice `visionMultipleAprilTag`.

### 15.2 프레임 처리

경계 듣기 안 순서: ① 끝난 전이 적용 ② 처리 중 프레임의 끝 e ≤ b면 결과를 내고(처리기의 `detections`·`detectionsUpdate`에 넣음) 대기 프레임을 바로 시작 ③ 새 `frameNanos`가 오면 STREAMING이 아니면 버리고, 처리 중이면 대기 칸 하나를 바꾸고[가정: 최신 프레임 하나 대기], 아니면 시작한다. 열기 전에 온 프레임은 마지막 본 시각만 바꾸고 버린다(다시 열어도 처리하지 않음). 처리기 `init`은 포털 수명에 한 번(첫 처리 프레임, 실제 `ProcessingPipeline.init`과 같음)이고 SandBot은 AprilTag 처리기만 부른다. 처리 중이던 프레임은 stop 뒤에도 결과를 내고, close는 그 결과의 끝까지 닫히지 않는다(EOCV `closeCameraDevice`가 프레임 작업을 끝냄).

FPS(`getFps`): EOCV `OpenCvCameraBase`처럼 처리 시작 간격(ms) 30개(`SANDBOT_FPS_SAMPLES` = 30, `MovingStatistics(30)`)의 평균이고 fps = 1/평균(초). 첫 표본 기준은 그 스트림의 `STARTING_STREAM` 시작(`prepareForStartStreaming`이 FPS 표본과 타이머를 새로 만든다)이라 낮게 시작해 차오른다.

### 15.3 처리 시간 표

T = T₀(d)·(w·h)/(640·480) ns, 정수 반올림(`StrictMath.round`). T₀는 640×480 기준 데시메이션에서 조각 선형이다.

| 데시메이션 d | T₀ (ms)          | 식   |
| ------------ | ---------------- | ---- |
| d ≤ 1        | 100              |      |
| 1 < d ≤ 2    | 100 − 55·(d − 1) | 직선 |
| 2 < d < 3    | 45 − 23·(d − 2)  | 직선 |
| d ≥ 3        | 22               |      |

상태: [가정: 처리 시간 표]. 근거: d 3은 실물 DS 화면("Pipeline: 19ms · Overhead: 3ms", 합 22 ms), d 1·2는 샘플 주석의 FPS뿐이다. 측정 방법: AprilTag 처리기 하나로 d 1·2·3의 `getFps()`와 DS 카메라 스트림의 Pipeline ms를 읽는다. 상태: 실측 필요(d 1·2).

계산값(프레임 격자 30 fps로 상한이 걸리기 전의 처리 속도 1/T):

| 해상도    | d   | T (ms) | 처리 속도(FPS)                                           |
| --------- | --- | ------ | -------------------------------------------------------- |
| 640×480   | 1   | 100    | 10.00                                                    |
| 640×480   | 2   | 45     | 22.22                                                    |
| 640×480   | 3   | 22     | 45.45(프레임 격자 30 fps로 약 30)                        |
| 1280×720  | 3   | 66     | 15.15                                                    |
| 1920×1080 | 1   | 675    | 1.48(close가 처리 끝까지 닫히지 않으므로 0.3 s보다 길다) |
| 640×480   | 1.5 | 72.5   | 13.79                                                    |
| 640×480   | 2.5 | 33.5   | 29.85                                                    |

CLAUDE.md는 C920 640×480이 d 3 약 30, d 2 약 22, d 1 약 10 FPS, 1280×720 d 3은 약 15 FPS라고 적었다.

### 15.4 웹캠 출력 키(`SimCamera.publish`)

`serialNumber`(구성에서, `SimWebcamName`)·`state`(`CameraState` 이름, 포털이 없으면 null)·`streaming`(STREAMING이면 true)·`width`·`height`·`aprilTag`(켜진 AprilTag 처리기 있음)·`family`·`decimation`(대기 중 `setDecimation` 값, 없으면 지금 값, 처음 3)·`fps`·`exposureMs`(Manual일 때 단위/10.0 ms, 아니면 null)·`gain` 순이다. 포털이 없는 출력(`publishIdle`)은 state null·streaming false·width/height null·aprilTag false·family null·decimation null·fps 0.0이다. 한 번에 포털 하나만 웹캠을 잡는다(`claim`).

### 17.3 `Calibration.findExtrinsicCameraParams`(ITERATIVE)

`cvFindExtrinsicCameraParams2`(왜곡 없음, `useExtrinsicGuess` 없음):

1. 영상 점 정규화 x = (u − cx)·(1/fx), y = (v − cy)·(1/fy)(곱 형태 `1*x + 0*y + 0`, ww = 1/(0·x + 0·y + 1)까지 OpenCV와 같은 연산 순서).
2. Mc = 물체 점 평균, MM = (M − Mc)ᵀ(M − Mc), SVD로 W·V를 얻는다.
3. W[2]/W[1] < 1e-3이면 평면 구조: V[2]² + V[5]² < 1e-10이면 R = I, det < 0이면 부호 반전, T = −R·Mc, 평면 좌표를 호모그래피(`cvFindHomography`)로 풀어 h1·h2 정규화(s1 = 1/max(‖h1‖, DBL_EPSILON), s2 = 1/max(‖h2‖, DBL_EPSILON), s3 = 2/max(‖h1‖ + ‖h2‖, DBL_EPSILON)), h3 = h1 × h2, R = H·Rt. 호모그래피에 비유한 원소가 있으면 R = I, t = 0.
4. 아니면 비평면: DLT. 점이 6개 미만이면 `CV_CheckGE(count, 6)` 오류(calibration.cpp:1280, "DLT algorithm needs at least 6 points for pose estimation from 3D-2D point correspondences"). 12×12 SVD의 가장 작은 특이 벡터로 RR·tt, det < 0이면 부호 반전, sc = ‖RR‖(DBL_EPSILON 이하면 오류), R = U·Vᵀ, k = ‖R‖/sc.
5. `CvLevMarq`로 다듬기: `maxIter` = 20, epsilon = `FLT_EPSILON`, 초기 λ = 10^−3(lambdaLg10 = −3), 오차가 늘면 lambdaLg10을 올려 재시도(16까지), 아니면 lambdaLg10 = max(lambdaLg10 − 1, −16). 반복 수는 1–1000으로 자른다. step은 (JᵀJ의 대각 × (1 + λ))·d = Jᵀe를 SVD로 푼다. 종료는 `++iters ≥ maxIter` 또는 `‖param − prevParam‖/(‖prevParam‖ + DBL_EPSILON) < epsilon`.
6. 호모그래피 다듬기 LM(`LMSolverImpl`): 반복 10회, eps = `FLT_EPSILON`.

`Ippe`: `IPPE_SMALL` = 1e-3(ippe.cpp:41)을 평면 판정(z 성분), 법선 판정 등에 쓴다. 호모그래피 행렬식 < 1e-9이면 "Determinant is zero!"(`IppeError`). `rot2vec`의 단위 행렬 판정은 `wNorm < FLT_EPSILON`이다. `Epnp`는 가우스–뉴턴 정제 5회(`iterationsNumber` = 5)를 쓴다.

## 20. 사이드카 알림(notice)

호스트가 `NOTICE_PARAM_KEYS`로 키를 확인한다(빠지거나 남으면 프로토콜 오류). 같은 code·params는 실행마다 한 번(`simNotice`). 값은 팀 파일·팀 코드의 글자(보정 XML 속성, 묶음 이름)를 담을 수 있어 런타임이 null을 `"null"`로 바꾸고 4096자로 자른다("…" 포함). 호스트는 매개변수가 16개(`MAX_NOTICE_PARAMS`)를 넘거나 키·값이 4096자(`MAX_NOTICE_TEXT`)를 넘거나 키 집합이 code의 표와 다르면 프로토콜 오류로 본다. 문구는 `console.notices.sim.*`다.

| code                         | params                     | 뜻                                                                                                     |
| ---------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------ |
| `visionProcessorUnsupported` | `processor`(바이너리 이름) | AprilTag 처리기가 아닌 처리기는 프레임을 받지 않는다                                                   |
| `aprilTagNoFieldPose`        | `cluster`                  | 묶음 metadata의 필드 자세가 0이라 robotPose가 묶음 틀 기준이다                                         |
| `visionSolverSubstituted`    | `solver`                   | SQPNP·APRILTAG_BUILTIN 단일을 ITERATIVE로 대신 푼다(렌더러가 solver로 `.sqpnp`·`.builtin` 문구를 고름) |
| `visionSolverStop`           | `solver`(error 바로 앞)    | 그 풀이가 묶음을 풀지 못해 OpenCV 예외로 OpMode가 멈춘다                                               |
| `visionMultipleAprilTag`     | 없음                       | 한 포털에 AprilTag 처리기가 둘 이상 켜져 있다                                                          |
| `visionFrameCapture`         | `method`                   | 프레임 저장은 영상이 없어 아무것도 하지 않는다                                                         |
| `visionResumeNullFormat`     | 없음                       | 스트림 형식 없이 `resumeStreaming`을 불러 STARTING_STREAM에 머문다                                     |
| `visionCalibrationSkipped`   | `detail`(영어 한 줄)       | `teamwebcamcalibrations.xml`의 보정 하나를 SDK 규칙대로 버린다                                         |

세계 쪽 `worldError`: `sensor <장치>`(거리·컬러 비유한 값), `camera <장치>`(tags 비유한 값)다(§8·§14).

## 23. 알려진 한계·남은 일

### 23.1 거리·컬러 센서(4c)

- 자기 로봇 몸체가 시뮬레이터 광선을 가리지 않는다(편집 자세 경고만, 실행 중 자세·관절 움직임의 가림은 경고하지 않는다). 다른 로봇도 없다.
- 광선이 경기 요소 공(6a)을 보지 않아(6c) 흡입구 컬러 센서는 늘 "물체 없음"(배경)이고, HIVE 몸체·CELL은 광선에 걸리지 않는다.
- 필드 밖(투명판 너머)은 형상이 없고(컬러는 배경 ρ 0.2), 판 이음 3 mm(23.335–23.460 in)는 지나가며, 벽 모서리 두 판의 이중 반사(ρ_eq ≈ 0.05)는 없다. 벽에 붙은 로봇의 앞면 센서는 판 inset 2.3 mm를 낸다(레일이 아니라 판 안쪽 면 기준).
- 낮은 센서는 1 m 근처에서 바닥 광선이 값을 짧게 만든다(h 5 cm면 1 m에서 −25 mm). 낮은(≤ 3 cm) 수평 ToF는 바닥과 먼 벽 거울이 섞인 중간 거리를 낸다. 얇은 표적(≤ 3 cm)은 0.5 m에서 바깥 고리 간격 2.6 cm 때문에 요 0.25°마다 값이 1–2 cm까지 계단처럼 바뀌고, 부분 표적은 B 보정 때문에 최대 0.8 % 짧다.
- 주변광·실외 모드·8191(signal fail)·다중 표적이 없고 컬러 잡음이 없다. ToF는 측정 끝 표본(33 ms, 1.5 m/s면 5 cm 사이)이고 창 평균이 없다. PS는 SDK 기본 설정 기준이다.
- 하우징 앞면은 형상 경계 상자의 조준 축 투영이라 형상이 없거나 큰 그룹에 붙이면 다르다(`farHousing`·`worldSensorNoHousing`). 거울 반환은 벽 투명판만이고(구조물·HIVE 스킨 없음) 컬러 센서에는 없다.
- 잡음은 세계가 칩 측정 격자를 몰라 틱 시각을 측정 번호로 쓴다(켜면 매 틱 보낸다).
- 실측이 필요한 값: 재질 표(§4.4), 폴리카보네이트 거울·헤이즈, 빔 모양·문턱 지수·흰색 1.2 m, 색 K·E_a·s(d)·ρ_ref·발자국 반경·배경, 잡음(`docs/assumptions.md` 4c 표).
- 4c는 `WORLD_SPEC_VERSION` 4·`PROJECT_VERSION` 10을 그대로 두었다(4c 시점의 값. 4ab 계약이 센서 목록·noise 모양과 검사를 이미 넣었다. 지금 값은 아래 4d 항목).

### 23.2 AprilTag 비전(4d)

- 영상이 없다(왜곡 투영·모션 블러·노출 효과·조명·오검출·부분 해독 없음, 다른 처리기는 프레임을 받지 않음, LiveView·DS 카메라 스트림·`saveNextFrameRaw` 파일 없음, `getFrameBitmap`은 `Continuation`이 stub이라 쓸 수 없음).
- 자기 로봇 몸체·다른 로봇·HIVE 몸체·득점 요소(6a 공, 6c에서 넣음)가 시야를 가리지 않는다(편집 자세 자기 가림 경고만). 가림은 태그 면 9점으로 본다(정확한 사각뿔 교차가 아님).
- 모델별 지원 해상도·최대 FPS·형식(YUY2·MJPEG) 차이가 없다(모든 해상도 30 fps, "지원하지 않는 해상도" 정지 없음). 정수가 아닌 데시메이션은 연속 값으로 본다. 캡처 틱과 처리 시작 사이에 `setDecimation`이 오면 그 한 프레임은 세계와 사이드카의 데시메이션이 다르다.
- 내장(폰)·스위처블 카메라는 unsupported로 멈춘다. SQPNP·APRILTAG_BUILTIN 단일은 ITERATIVE로 대신한다(잡음이 있으면 실제와 조금 다르고 BUILTIN 단일의 이동은 실제와 달리 float로 잘린다). EPNP의 조건이 나쁜 경우는 플랫폼에 따라 실제끼리도 값이 다를 수 있다.
- `getPerTagAvgPoseSolveTime`은 0이다. 해가 0개면 rvec·tvec는 0이다(실제는 초기화하지 않은 메모리).
- 형식 없는 resume에서 실제 NPE가 앱을 멈추는지, 같은 웹캠을 두 포털이 열 때의 실제 동작은 확인하지 못했다. `CameraCalibrationManager` API·`getCameraCharacteristics`는 stub이다.
- 카메라 제어 값 범위는 모델과 관계없는 가정이고 시뮬레이터에 영향이 없다.
- OpenCV를 품은 팀 라이브러리 jar는 부모 먼저 로더 때문에 가짜 SDK의 OpenCV 클래스에 가려진다(`archive.ts` `PROTECTED`에 `org/opencv/`를 넣지 않았다. 실제 로봇에서도 같은 클래스가 둘이면 dex 병합이 실패한다). Limelight·HuskyLens의 AprilTag 결과는 없다.
- 실측이 필요한 값: 처리 시간 표(d 1·2), 최소 변·모서리 각·흰 테두리, 포털 전이 시간, decisionMargin, 잡음 σ, 다른 종횡비 렌즈 값(C310·C270·LifeCam), OpenCV 오류 줄 번호(`docs/assumptions.md` 4d 표).
- 4d는 `WORLD_SPEC_VERSION` 5·사이드카 프로토콜 4이고 `PROJECT_VERSION`은 10 그대로다(4d 시점의 값). 지금 코드는 `PROJECT_VERSION` 14(4e 필드 CAD v11, 코드 단위 설정 v12, 충돌체 v13, Preload Slot v14)·`WORLD_SPEC_VERSION` 7(충돌 v6, 경기 요소 v7)·`SIDECAR_PROTOCOL_VERSION` 4다. 웹캠 `cameras`는 세계 설명 v5에서 생겼고 v4는 받지 않는다(`parseWorldSpec`은 v7만 받는다).
