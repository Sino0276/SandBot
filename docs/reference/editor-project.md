# 에디터·프로젝트 파일·좌표·단위·코드 생성 기준 문서

이 문서는 SandBot 에디터의 "씬 문서"가 지켜야 하는 규약과 숫자를 한곳에 모은 기준 문서다. 범위는 다섯 가지다. (1) 좌표계(필드·로봇·CAD)와 회전 순서, 좌표 변환 함수(`scene/model.ts`, `scene/coordinates.ts`, `cad/alignment.ts`). (2) 단위 세 층(내부 미터·라디안, 개인 표시 단위, 프로젝트 코드 단위)과 변환 경계(`units/`, `hardware/codeUnits.ts`, `scene/projectSettings.ts`). (3) 프로젝트 파일 `sandbot/project.json`의 형식·검증·`PROJECT_VERSION` 1–14 변경 이력(`project/projectFile.ts`, `scene/*`의 바퀴·질량·관절·충돌체·프리로드 설정 범위). (4) 하드웨어 카탈로그(구성 XML 태그·Java 타입·I2C 주소·포트 범위·속성, `hardware/catalog.ts`)와 검증(`hardware/validation.ts`). (5) 코드 생성 규칙(Java 하드웨어 클래스·로봇 구성 XML·생성 파일 표식)과 오프셋 계산 규약(Pinpoint·OTOS·데드휠·IMU·센서·카메라 장착, `hardware/mounting.ts`). 값의 원천은 코드(상수·주석)이고, 의도는 CLAUDE.md와 `docs/assumptions.md`에서 가져왔다. 코드가 출처를 적지 않은 값은 "출처 기록 없음"이라고 썼고 출처·데이터시트 숫자를 지어내지 않았다. 시뮬레이터 물리·센서·충돌·공의 상세는 각 단계 문서(`mass.md`·`motors-joints.md`·`drivetrain.md`·`field-biobuzz.md`·`sensors-vision.md`·`collision.md`·`balls-6a.md`·`sidecar-time.md`)의 몫이고, 여기서는 이 영역이 정하는 설정 칸의 모양·범위·기본값과 연결만 다룬다.

주석이 가리키는 `spec-3b §…`, `spec-4c §…`, `spec-4d §…`, `spec-4e §…`, `spec-5 §…`, `synthesis §…`, `critique E13` 같은 문서 번호는 대부분 원본이 사라져(§18) 이 저장소에서 따라갈 수 없다. 그런 번호는 "주석 인용"으로만 적었다.

### 0.2 표기 규약

- 위치 열의 파일 경로는 따로 적지 않으면 `src/renderer/src/` 기준이다. `src/shared/…`·`src/main/…`는 저장소 루트부터 적는다. 줄 번호는 적지 않는다.
- 코드의 길이는 미터, 각은 라디안이다. 표의 `in`·`°`는 환산이다(1 in = 0.0254 m).
- 회전 벡터는 `[롤(X), 피치(Y), 요(Z)]` 라디안이다.

## 2. 좌표계·회전·변환 함수

### 2.1 세 좌표계

| 좌표계                   | 정의                                                                                                                              | 위치                                                        | 상태·근거                                                                                                                                              |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 필드(저장 좌표)          | FTC 필드 좌표계. 원점 필드 중앙 타일 윗면, Z 위, 축은 그 시즌의 공식 좌표계(시즌 필드 행). 단위 미터·라디안, 각은 반시계 +        | `scene/coordinates.ts` 머리 주석, CLAUDE.md "좌표계"        | 설계 결정. 시즌별 축 방향은 `field-biobuzz.md` §1.1(BIOBUZZ는 +X 관중석 벽, +Y 파랑 벽, −Y 빨강 벽). `'none'` 시즌은 타일 두께가 없어 바닥과 같은 평면 |
| 로봇                     | X 앞, Y 왼쪽, Z 위. 원점은 로봇 중심 바닥(CAD 정렬 뒤 경계 상자 바닥 면 중심)                                                     | CLAUDE.md "좌표계", `cad/alignment.ts` `cadRootTransform`   | 설계 결정                                                                                                                                              |
| CAD(STEP 파트의 자기 축) | CAD 파일의 축. Y-up CAD면 Y가 위. 정렬은 CAD 루트 transform 하나가 맡는다. 불러올 때 CAD 루트 아래 노드는 회전 없이 위치만 가진다 | CLAUDE.md "좌표계", `cad/stepImport.ts` `buildSceneObjects` | 설계 결정                                                                                                                                              |

- 씬 오브젝트의 `transform`은 부모 기준 로컬 값이고 최상위는 필드 좌표다(`SceneObject.transform` 주석). 좌표 변환은 `scene/model.ts`의 함수(`getTransformInFrame`·`localTransformFromWorld` 등)로만 한다(CLAUDE.md 불변 조건).
- 이동·회전 핸들 축 전역/로컬은 핸들 방향에만 적용한다(인스펙터 값은 늘 부모 기준 `transform`).
- 로봇 안 오브젝트에는 로봇 중심 기준 위치(`getTransformInFrame(…, 'robot')`)를 읽기 전용으로 함께 보인다. 로봇 좌표계는 계산(로봇 중심 기준 위치, 센서 오프셋)에 쓴다.
- Z-up은 `scene/coordinates.ts`가 `Object3D.DEFAULT_UP.set(0, 0, 1)`로 적용한다. Object3D를 만드는 코드보다 먼저 평가되어야 하므로 `main.tsx`가 가장 먼저 import한다.

### 2.3 `matrixToTransform`(ZYX 오일러 추출)

Three.js `Euler.setFromRotationMatrix`는 |m31| ≥ 0.9999999에서 짐벌 식으로 바꿔 피치 ±90° 근처에서 1.6e-4 rad까지 틀린다(부모 바꾸기·CAD 정렬이 자주 지나는 영역, 코드 주석). 그래서 직접 구한다.

알고리즘(행렬 R, 3×3 회전 부분. 코드의 열 우선 배열 e에서 R[0][0] = e[0], R[1][0] = e[1], R[2][0] = e[2], R[0][1] = e[4], R[1][1] = e[5], R[0][2] = e[8], R[1][2] = e[9]):

1. `decompose`로 위치·쿼터니언을 뽑고 쿼터니언에서 다시 회전 행렬을 만든다(척도를 버림).
2. cosP = hypot(R[0][0], R[1][0]). 피치 = atan2(−R[2][0], cosP). (asin이 아니라 atan2이므로 극 근처에서도 정확하다.)
3. cosP < 1e-12(짐벌)이면 롤 = 0, 요 = atan2(−R[0][1], R[1][1]).
4. 아니면 요 = atan2(R[1][0], R[0][0]). 롤은 "요를 되돌린 나머지 회전 Rz(−요)·R = Ry(피치)·Rx(롤)"의 크기 1짜리 원소에서 구한다: 롤 = atan2(sin(요)·R[0][2] − cos(요)·R[1][2], cos(요)·R[1][1] − sin(요)·R[0][1]). 극 근처에서는 요 오차가 작은 두 값에서 오므로 덜 정확하지만 롤이 그 오차를 메워 행렬은 정확히 되돌아온다.
5. 극에서 먼 곳에서는 Three.js와 반올림 오차 안에서 같은 값이다.

### 3.2 정렬(`cad/alignment.ts`)

CAD 프로그램마다 위·앞 축이 달라 파일마다 방향을 고른다. 기본값은 마지막에 고른 방향(개인 설정 `sandbot:cadAlignment`, `cad/alignmentPreference.ts`가 `{ upAxis, forwardAxis }` JSON으로 읽고 쓴다), 처음에는 Y-up(`DEFAULT_ALIGNMENT` = `ALIGNMENT_PRESETS.yUp`). 저장값이 없거나 JSON이 깨졌거나 축 방향이 아니거나 위·앞 축 글자(X·Y·Z)가 같으면 `DEFAULT_ALIGNMENT`를 쓴다.

| 프리셋 | 위 축 | 앞 축 | 해당 CAD                                    | 로봇 Y(왼쪽)가 가리키는 CAD 축 | 정렬 회전의 ZYX 오일러(계산값) |
| ------ | ----- | ----- | ------------------------------------------- | ------------------------------ | ------------------------------ |
| `yUp`  | +Y    | +Z    | Fusion 360 기본, SolidWorks, Inventor(주석) | +X                             | [90°, 0°, 90°]                 |
| `zUp`  | +Z    | −Y    | Onshape, Z-up으로 설정한 Fusion 360(주석)   | +X                             | [0°, 0°, 90°]                  |

- 축 방향 6개: `+X −X +Y −Y +Z −Z`(`AXIS_DIRECTIONS`). 유효한 정렬은 위 축과 앞 축의 글자(X·Y·Z)가 다른 것(`isValidAlignment`: `upAxis[1] !== forwardAxis[1]`).
- 보조 함수: `axisVector(axis)`는 축 방향 하나의 단위 벡터(부호 `-`이면 −1), `boundsCenter(bounds)`는 경계 상자 중심(min·max 평균, 노드 피벗), `findPreset(alignment)`는 `ALIGNMENT_PRESETS` 중 위·앞 축이 모두 같은 프리셋 이름(없으면 null).
- 왼쪽 축: left = up × forward(외적). 정렬 회전 행렬 R(CAD → 로봇)은 행이 forward, left, up 순서(각 행이 로봇 X·Y·Z 축을 CAD 좌표로 나타냄)다. 따라서 CAD forward 축이 로봇 +X, CAD up 축이 로봇 +Z가 된다.
- Y-up 열 해석(계산값): CAD X → 로봇 Y(왼쪽), CAD Y → 로봇 Z(위), CAD Z → 로봇 X(앞). 이는 필드 CAD 보기 기본 정렬 "FTC (X, Y, Z) = (CAD z, x, y)"(`scene/fieldDoc.ts` `DEFAULT_FIELD_VISUAL_ALIGNMENT`)와 같은 순환 치환이다(거울상이 아님).
- Z-up 열 해석(계산값): CAD X → 로봇 Y, CAD Y → 로봇 −X, CAD Z → 로봇 Z.

CAD 루트 변환 `cadRootTransform(bounds, alignment)`:

1. R = `alignmentRotation(alignment)`.
2. CAD 경계 상자 8꼭짓점을 R로 돌려 min·max를 구한다.
3. offset = (−(min.x + max.x)/2, −(min.y + max.y)/2, −min.z). 곧 정렬한 모델의 바닥 면 중심(x·y 중심, z 최저)이 로봇 원점에 온다.
4. 피벗(경계 상자 중심)의 위치 = R·center + offset.
5. 결과 변환 = `matrixToTransform(R의 회전 + 위치 pivot)`.

예(계산값): CAD 경계 min (−0.2, 0, −0.2), max (0.2, 0.4, 0.2)를 Y-up으로 정렬하면 CAD 루트 위치 (0, 0, 0.2), 회전 [90°, 0°, 90°]. Z-up이면 위치 (0, 0, 0.2), 회전 [0°, 0°, 90°].

- 정렬을 바꾸면 `setCadAlignment`가 바닥 중심 맞춤을 다시 계산하고, 그 CAD 밖으로 옮긴 노드(`cadOrigin`)도 같은 만큼 움직인다(CLAUDE.md).
- 필드 CAD는 위치를 옮기지 않고 회전만 쓴다(CAD 원점 = 필드 원점, `alignmentRotation`만 사용). 로봇 CAD 방향 기억은 필드 CAD가 읽지도 쓰지도 않는다(`field-biobuzz.md` §16).

오브젝트마다 `cad`는 저장 꼴이 다르다: `absolutePath`를 빼고 `file: { relativePath, absolutePath }`를 붙인다. `relativePath`는 `relativize(absolutePath)`(프로젝트 기준 상대 경로, preload가 `/` 구분으로 만듦), `absolutePath`가 빈 문자열이면 `null`이다. STEP은 복사하지 않고 원래 위치를 상대·절대 경로로 함께 기억한다. 열 때는 상대 경로 → 절대 경로 순으로 찾는다. 빈 `scripts` 배열은 쓰지 않는다.

## 8. 하드웨어 카탈로그

`hardware/catalog.ts` 머리 주석: "XML 태그·Java 클래스·I2C 주소는 FTC SDK 12.0 소스(10.3·11.1과 동일)에서 확인한 값만 쓴다. 구성 XML 태그는 대소문자를 구분하고, 틀리면 SDK가 오류 없이 장치를 버리므로 추측한 값을 넣지 않는다." 따라서 아래 §8.2의 태그·타입·주소는 [확인: FTC SDK 12.0 소스]다. 카탈로그 주석 자체에는 소스 파일·줄 번호가 없지만, 실제 SDK 12.0 소스에서 옮긴 사이드카 손 구현(`sidecar/sdk`)이 같은 값을 선언하므로 이 저장소 안에서 대조할 수 있다(§8.2.1). 가짜 SDK(사이드카)는 카탈로그의 Java 타입을 모두 지원해야 한다(CLAUDE.md).

### 8.4 속성 정의(`properties`)

속성 기본값은 `propertyDefaults(type)`(속성 키 → default)이고, 인스펙터에서 보이는지는 `isPropertyVisible(property, props, jointTypeOf)`가 `visibleWhen`(다른 enum 속성 값이 `values`에 있는지)과 `visibleWhenJoint`(그 object 속성이 가리키는 오브젝트의 관절 형식, `types`가 있으면 그 안일 때만)로 정한다(값은 늘 저장). 속성 종류(`PropertyDef.kind`): `enum`(options·default), `number`(default·min?·max?·digits·zeroBelow?), `length`(내부 m, 표시 단위로 입력, default·min·max), `angle`(내부 rad, 인스펙터는 °, `wrap`이면 (−π, π]로 감고 아니면 [min, max]로 자름), `text`, `object`(씬 오브젝트 id, `pick`: `'any'` 같은 로봇의 오브젝트 / `'joint'` 같은 로봇의 관절 오브젝트). 공통 메타: `visibleWhen`(다른 enum 속성 값이 일치할 때만 보임, 값은 늘 저장), `visibleWhenJoint`(다른 object 속성이 관절이 있는 오브젝트를 가리킬 때만, `types`로 형식 제한), `hint`(칸 설명 `hardware.propHints.<key>`), `simulation`(시뮬레이터 전용: 생성 Java·구성 XML에 쓰지 않으므로 바꿔도 생성 파일은 바이트 단위로 같다, `generatedOutput.test.ts`가 확인).

### 8.6 허브 방향(IMU)

`HUB_DIRECTION_VECTORS`(`RevHubOrientationOnRobot` 방향 → 로봇 좌표 벡터, LEFT/RIGHT는 로봇 뒤에서 본 방향): up (0,0,1), down (0,0,−1), forward (1,0,0), backward (−1,0,0), left (0,1,0), right (0,−1,0). 로고 방향과 USB 방향이 같은 축이면(내적 ≠ 0) 물리적으로 불가능하다(SDK가 `IllegalArgumentException`을 던진다, `isValidHubOrientation`).

### 10.1 이름 변환(`hardware/naming.ts`)

| 함수                                        | 규칙                                                                                                                                                                                                                                                                                                                                                                                                                                       |

| `javaClassName(name)`                       | 같은 방식으로 나눈 단어마다 ASCII 소문자 첫 글자만 대문자로 바꿔 붙인다(한글 등은 그대로라 `isValidGroupClassName`을 통과하지 못함). `lift arm` → `LiftArm`, `Group (1)` → `Group1`, `LIFT` → `LIFT`                                                                                                                                                                                                                                       |
| `isValidGroupClassName`                     | `/^[A-Z][A-Za-z0-9]*$/`. 중첩 클래스는 `RobotHardware$Lift.class`가 되므로 ASCII만 쓴다(한글 파일 이름은 javac 환경에 따라 실패). `$`는 다른 중첩 클래스와 바이너리 이름이 겹칠 수 있고(`Lift$Claw`와 `Lift.Claw`) `_`는 상수 이름과 구별하려고 뺀다                                                                                                                                                                                       |
| `groupFieldName(className)`                 | 앞의 대문자 묶음을 소문자로 바꾼다. 묶음 뒤에 소문자가 오면 묶음의 마지막 대문자는 다음 단어의 첫 글자이므로 남긴다. `Lift` → `lift`, `LIFT` → `lift`, `IMU2` → `imu2`, `HTTPServer` → `httpServer`. 키워드·`hardwareMap`이면 `_`. 클래스(대문자)와 필드(소문자)가 같아지지 않게 한다(같으면 `RobotHardware.Lift.X`의 `Lift`를 Java가 필드로 읽는다)                                                                                       |
| `constantName(identifier)`                  | 앞의 `_`를 지우고 (소문자·숫자)(대문자) 사이에 `_`를 넣은 뒤 대문자로. 비었거나 숫자로 시작하면 `_`를 앞에 붙인다. `frontLeft` → `FRONT_LEFT`, `_2mSensor` → `_2M_SENSOR`                                                                                                                                                                                                                                                                  |
| `generatedConstantNames(type, name, units)` | `constantName(javaIdentifier(name))` + `constantSuffixes(type, units)` 각각                                                                                                                                                                                                                                                                                                                                                                |
| `isValidJavaClassName`                      | `/^[A-Za-z_][A-Za-z0-9_]*$/`이고 키워드·`_`·Windows 장치 이름이 아님. `$`는 받지 않는다(그룹 중첩 클래스 `Bot$Lift`가 다른 로봇 클래스와 겹침)                                                                                                                                                                                                                                                                                             |
| `javaString`                                | 큰따옴표 문자열 리터럴: `\`·`"`·줄바꿈·CR·탭을 이스케이프                                                                                                                                                                                                                                                                                                                                                                                  |
| `xmlAttribute`                              | `&`·`<`·`>`·`"`·`'`를 `&amp;`·`&lt;`·`&gt;`·`&quot;`·`&apos;`로                                                                                                                                                                                                                                                                                                                                                                            |
| `sidecarDeviceName`                         | 사이드카가 구성 XML의 name을 장치 이름으로 쓰는 규칙(Java `String.trim`): 앞뒤의 U+0020 이하 글자만 뺀다. JS `trim()`은 NBSP·U+3000·BOM도 빼지만 Java는 남기므로 쓰지 않는다                                                                                                                                                                                                                                                               |

Java 키워드 목록(`JAVA_KEYWORDS`): abstract assert boolean break byte case catch char class const continue default do double else enum extends final finally float for goto if implements import instanceof int interface long native new package private protected public return short static strictfp super switch synchronized this throw throws transient try void volatile while true false null var record yield sealed permits. 생성 코드가 직접 쓰는 예약 필드 이름은 `hardwareMap`(생성자 매개변수를 가림). 이름에 쓸 글자가 하나도 없을 때의 필드 이름은 `device`(`_`는 Java 9부터 키워드).

### 10.2 코드 범위 트리(`codeScopes.ts`)

클래스·필드·상수 이름은 `codeScopes.ts`가 한 번 정하고 코드 생성과 검증이 같이 읽는다(둘이 다른 이름을 보면 검증을 통과한 파일이 Android Studio에서 컴파일되지 않는다).

| 규칙                 | 내용                                                                                                                                                  |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 뿌리                 | 로봇 클래스(`hardware.className`). `classPath` = [클래스], `fieldPath` = []                                                                           |
| 그룹                 | 장치가 있는 `kind: 'group'` 오브젝트마다 중첩 클래스 하나(`public static final class`). 클래스 이름 = `codeClassName.trim() \|\| javaClassName(name)` |
| 그룹 필드            | 클래스 이름이 유효하면 `groupFieldName(className)`, 아니면 표시용으로 `javaIdentifier(name)`                                                          |

| 멤버 순서            | 하이어라키 순서. 오브젝트 자신의 장치가 먼저, 그다음 자식. 그룹이 아닌 자식(assembly·part)의 장치는 가까운 상위 범위에 들어간다                       |
| 장치 필드            | `javaIdentifier(구성 이름)`. 그룹 안에서도 같은 이름(`robot.lift.liftLeft`)                                                                           |
| 카탈로그에 없는 종류 | 코드를 만들지 않는다                                                                                                                                  |
| 캐시                 | 불변 문서·`codeUnitsKey`·로봇 id마다 한 번(WeakMap)                                                                                                   |
| 그룹이 없는 로봇     | 출력이 바이트 단위로 같아야 한다(`generatedOutput.test.ts`의 파일 스냅샷)                                                                             |

## 11. 코드 생성: Java 하드웨어 클래스

`generateHardwareJava(objects, robotId, units)`(`hardware/javaCodegen.ts`). 검증 오류가 없는 상태에서 부른다. 생성 Java의 주석은 팀이 Android Studio에서 읽으므로 영어로 쓴다. 주석에 넣는 이름은 `commentText`로 거른다: `\` → `\\`, `*/` → `* /`, 줄바꿈·U+2028·U+2029 → 공백(javac는 주석 안의 `\u` 이스케이프도 먼저 해석하므로 잘못된 `\u`는 컴파일 오류, `\u000a`는 줄바꿈). 들여쓰기는 4칸.

### 11.1 파일 구조

1. 머리 주석 두 줄: `// Generated by SandBot. Do not edit: this file is overwritten every time the SandBot project is saved.`, `// @sandbot-generated <내용 해시>`(§13.1).
2. `package org.firstinspires.ftc.teamcode.sandbot;`
3. `import` 정렬 목록(로봇 장치가 쓰는 import + `com.qualcomm.robotcore.hardware.HardwareMap`).
4. 클래스 Javadoc: 로봇 이름, DS 구성 이름 활성화 안내(`TeamCode/<구성 XML 경로>`), 사용 예 `<클래스> robot = new <클래스>(hardwareMap);`
5. `public class <className>`: `public static final String CONFIGURATION_NAME = "<configName>";`
6. 본문 블록(블록 사이 빈 줄 하나): 상수 → 필드(하이어라키 순서, `public final <Java 타입> <필드>;`) → 생성자 → 중첩 클래스들. 빈 블록은 빼고, 생성자 Javadoc `Call during OpMode init (hardwareMap.get must only be used in the init phase).`
7. 생성자 안은 장치마다 `// <구성 이름>` 주석 + 초기화 줄이고 장치 사이에 빈 줄. 그룹은 `// <그룹 이름>`, `<field> = new <Class>(hardwareMap);`.
8. 중첩 클래스 Javadoc: `Group "<이름>" in SandBot (robot.<필드 경로>). To use only this group in an OpMode:` + 사용 예 + `Construct either <바깥 클래스> or this group, not both: each one initializes this hardware.`(둘 이상 바깥이면 `Construct only one of <목록> or this group: …`). 생성자가 public이라 그 메커니즘만 쓰는 OpMode에서 따로 만들 수 있으나 둘 다 만들면 초기화(엔코더 초기화·IMU `initialize` 등)가 두 번 일어난다.
9. 장치 `get`: `<필드> = hardwareMap.get(<Java 타입>.class, "<구성 이름>");`

## 12. 코드 생성: 로봇 구성 XML

| 루트                  | `<Robot type="FirstInspires-FTC" name="<configName>">`                                                                                                                                                         |

### 13.3 생성 코드와 사용자 코드 분리

생성 코드와 사용자 코드는 분리한다. 인스펙터 속성에서 만들어지는 코드(hardwareMap 매핑 등)는 다시 생성해도 사용자가 작성한 스크립트를 덮어쓰지 않는다(CLAUDE.md 불변 조건). 생성 코드는 연결 파일(스크립트)을 참조하지 않는다. 시뮬레이터 전용 속성(`simulation: true`)·바퀴·질량·관절·충돌체·프리로드는 생성 출력에 영향을 주지 않는다(새 속성이 없던 씬의 생성 출력은 바이트 단위로 같다).

## 14. 오프셋·장착 계산 규약

`hardware/mounting.ts`. 장치가 로봇에 달린 위치·방향에서 SDK가 요구하는 설정값을 계산한다. 로봇 좌표계는 X 앞, Y 왼쪽, Z 위, 원점은 로봇 중심 바닥이다. 파트의 로봇 기준 위치는 `robotFramePose(objects, id)` = `getTransformInFrame(…, 'robot')`의 위치(x, y, z)와 요(`rotation[2]`)다(피벗 기준). 코드 주석은 "로봇에 속하지 않으면 null"이라고 적었지만 코드는 오브젝트가 씬에 없을 때만 null을 돌려준다. 로봇에 속하지 않은 오브젝트는 `getTransformInFrame`이 필드 기준으로 대신하므로 필드 좌표가 그대로 나온다(Pinpoint는 `pinpointComponentOffsetsMeters`가 `findRobotId`를 따로 확인해 걸러낸다).

## 17. 알려진 한계·남은 일

- 하드웨어 카탈로그 종류는 위 19개뿐이다. 다른 SDK 장치(색 센서 V2, 외부 IMU 등)는 카탈로그에 없다. 시뮬레이터 쪽 한계(CLAUDE.md): OctoQuad는 표현하지 않고, Limelight·HuskyLens의 AprilTag 결과는 없다.
- `otos`의 `linearScalar`·`angularScalar` 범위(0.872–1.127)는 카탈로그 주석에 출처가 없지만 사이드카 손 구현 `SparkFunOTOS.MIN_SCALAR`·`MAX_SCALAR`와 SDK 샘플 주석이 같은 범위를 적고 있다(§8.4). 모터 `stallTorque`·`freeSpeed` 덮어쓰기 범위는 `actuatorData.ts` 주석에 근거(표시 자릿수 한 칸, goBILDA 188:1 정지 토크·맨 모터 6000 rpm, 세계 설명 한도)가 있다(§8.4). 둘 다 제조사 데이터시트 같은 일차 출처는 아니다.
- 카탈로그의 XML 태그·타입·I2C 주소는 SDK 12.0 소스에서 확인했다고만 적혀 있고 파일·줄 번호는 카탈로그에 없다. pinpoint·otos·거리·컬러·터치·blinkin·huskyLens·octoQuad·analogInput·digitalDevice 태그와 일부 주소는 사이드카 손 구현이 같은 값을 선언한다(§8.2.1). 모터 태그·형식 값은 `MotorConfigurationType.java`가 선언한다. imu(0x28)·led·limelight·webcam 태그의 SDK 선언은 이 저장소에서 찾을 수 없다. 사이드카 빌드가 받는 해시 고정 SDK(`pnpm fetch:ftc-sdk`)로 다시 대조할 수 있다.
- `parseProps`의 `number` 속성은 범위를 검사하지 않는다(유한 수면 받는다). `length`·`angle`만 범위를 본다.
- `cad` 읽기는 `upAxis`·`forwardAxis`의 글자가 같은지(`isValidAlignment`)를 검사하지 않는다(필드 CAD `visual`은 검사한다).
- 인스펙터에서 바꾼 모터 방향 자체가 실제 로봇과 다른 것은 시뮬레이터가 잡지 못한다(CLAUDE.md).
- Unity 인스펙터와 회전 적용 순서(ZYX)가 같은지는 코드에 기록되어 있지 않다.
- 프로젝트 열기 중(CAD 위치 찾기) 시즌·오브젝트를 고치면 실행 취소·dirty 없이 연 상태에 들어간다(전부터 있던 구멍, CLAUDE.md 4e 한계).
- 로봇 CAD는 열 때 못 찾은 채 저장하면 저장한 사람의 절대 경로로 상대 경로를 다시 계산해 원래 상대 경로를 잃는다(필드 CAD만 고쳤다, CLAUDE.md 4e 한계).
- 이 영역의 미결정(CLAUDE.md): Pedro Pathing 경로 그리기, macOS·Linux 네이티브 STEP 변환기 배포. 추측해서 정하지 말고 사용자에게 확인한다.
- 실측·팀 칸으로 바꿀 값: 관절 기본 한계·마찰, 리밋 스위치 눌림 거리, Collider 마찰(0.4), 하우징 앞면 경고 거리(`docs/assumptions.md`).
